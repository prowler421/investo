## 1. What M2 delivers

ROADMAP M2's goal: `investo facts AAPL --lookback 5y` prints clean annual and quarterly statements
with a coverage report.

M1 fetches bytes and turns them into typed rows keyed by **XBRL tag**. M2 decides which tag answers
to "revenue," reconciles the four traps §4.2 documents, and emits a `FinancialHistory` in which
every figure is keyed by `Metric` and traces to a `SourceRef` or a `Derivation` over several. It is
the last stage at which a number can be wrong quietly: after M2, a bad figure is a bad chart, and
before M2 it is a parse failure. In between it is a plausible number with the wrong tag behind it.

### The three exit criteria, and where each is tested

| Exit criterion | Test | Status |
|---|---|---|
| ≥90% coverage across 20 NASDAQ names, on **both** metric tiers | `tests/coverage_probe.py` (marked `network`), recorded in `docs/m2/COVERAGE.md` | **blocked** — needs a denominator ([spec question 2](#7-spec-questions)) and the curated fixture set |
| Every fixture's expected series asserted exactly | the `test_facts_*` and `test_tags*` suites | **partially blocked** — see below |
| `as_of` demonstrably excludes later restatements | `test_facts_asof::test_restater_at_2021_06_30_yields_the_first_filing` | ready; the fixture exists and `PROVENANCE.md` already records the expected answer |

The second criterion needs a caveat that should not be discovered at review. Every fixture is
synthetic, generated by `tests/make_fixtures.py`; ROADMAP records curation as one of M1's three
unfinished items. **Asserting an exact value against a payload that says so because the generator
was told to say so tests the generator.** So M2's tests assert *derivations* — that NOQ4's FY2023
yields four quarters and not five, that the NCI-aware liabilities derivation differs from the
tempting one by exactly the NCI — which is CLAUDE.md's rule anyway and which survives the synthetic
set intact. Exact-value assertions against real filings arrive with curation.
[`05-testing.md` § 2](05-testing.md#2-fixtures) is explicit about which rules are settled today and
which six are not testable by anything currently on disk.

## 2. Considered and rejected: an M2a/M2b split

M1 split, and the tier boundary in §4.2 looks like an invitation to do it again: tier 1 feeds M3,
tier 2 feeds only M4's F/Z/M scores, so "M2a = pipeline + tier 1, M2b = tier 2 before M4" is the
same shape as M1a/M1b and would move a week off the critical path to the first PDF.

**It would move about a day, and it is not worth the risk.** The chains are declarative data in
one registry ([`01-tags.md` § 2](01-tags.md#2-the-chain-declaration)); once period-wise resolution,
exclusivity, unit filtering and sign handling exist, tier 2 is eleven more rows and one non-trivial
member (`SGA`). The expensive parts — `facts.py`'s five-guard residual recovery, the period spine,
the coverage arithmetic, the serializer's determinism rules — are shared by both tiers and are on
the critical path either way. Against that, ROADMAP M2 says in terms: *"Building only the first
tier means M4 stalls."* Deferring a day to re-incur a risk the plan already names is a bad trade,
and unlike M1b there is no separate machinery to defer — just table rows.

**There is a real slice here, and it is not the tier split.** Two of M2's workstreams are research
rather than coding, are unblocked by everything, and have no green test to declare them finished:
the carried-over fixture curation, and the twenty-name coverage measurement. Both should start on
day one in parallel, for the reasons `docs/m1/README.md` gives about the first of them — *"it is
done when a claim is verified, not when code runs, which is exactly how a task silently eats three
days while the code looks complete."* Sized separately in [§ 9](#9-sizing).

**And each one gates something that would otherwise be declared done on no evidence.** This is the
ordering constraint the parallelism exists to satisfy, and it is stated as a rule because both
gates are easy to walk past while the code is green:

| Workstream | Gates | Consequence of skipping it |
|---|---|---|
| Fixture curation | Exit criterion 2 — "every fixture's expected series asserted exactly" | Value assertions test `make_fixtures.py`. The derivation assertions still hold, so the suite is green either way; nothing fails to tell you. |
| Coverage measurement | Exit criterion 1, **and** [spec question 6](#7-spec-questions) | The eleven tier-2 chain orderings are this document's proposals, not measurements. They must **not** be folded into DESIGN §4.2 until the frames pull confirms them — otherwise a guess becomes normative by having been written down, and the tier-2 half of the 90% criterion is gated on chains nobody checked. |

So the tier-2 orderings are **provisional until `COVERAGE.md` exists**, and the revision lands in
the same commit as the measurement. Tier 1's orderings are not provisional: §4.2 carries measured
entity counts for every member.

## 3. `investo facts` — the command surface

`facts` already declares `--lookback`, `--as-of`, `--refresh`, `--cache-dir` and `--config` (M0),
with a body that raises `NotImplementedYetError.at("M2", …)`. That is the whole surface it needs,
plus one addition raised as [spec question 4](#7-spec-questions).

The body becomes `run_fetch` followed by `build_history` — the same wiring `fetch` already uses,
with no second fetch path:

```python
settings  = _settings(config_file=config_file, cache_dir=cache_dir, lookback=lookback)
years     = parse_lookback(settings.lookback)
resolved  = _resolve_as_of(as_of) or date.today()   # the clock is read HERE and only here
result    = run_fetch(ticker, settings=settings, refresh=refresh, as_of=resolved)
history   = build_history(
    result.facts,                    # CompanyFacts | None — an absence, not an error
    ticker=ticker, cik=result.cik, name=result.name,
    profile=result.profile,          # CompanyProfile | None — likewise
    filings=result.filings,
    window=window(years, as_of=resolved),
    as_of=resolved,
    market_cap=result.market_cap,
)
print(serialize(history, run=...) if json_ else render_facts(history))
```

Three things that snippet is making explicit rather than eliding:

- **`date.today()` is called at the command and nowhere below it.** `cli.py` and `fetch.py` are the
  only modules permitted to; `normalize/` and `report/` are forbidden by an AST rule
  ([`05-testing.md` § 4](05-testing.md#4-new-layering-rules)). A default resolved deeper makes two
  runs either side of midnight differ, which §11 reports as nondeterminism rather than as the
  design mistake it is.
- **`facts` and `profile` are passed as the `| None` they are.** Both have live absence paths in
  M1 (`fetch.py:191` and `:253`), both are documented as exit-0 outcomes in
  [§ 4](#4-exit-codes), and a non-optional `build_history` would neither type-check nor survive the
  first thin-coverage ticker. [`03-statements.md` § 1](03-statements.md#both-payloads-are-optional-because-m1-already-makes-them-optional).
- **`cik` and `name` come from the resolved ticker row**, not from `profile`, so they survive a
  404 on submissions. A ticker that did not resolve exited 2 before this line was reachable.

That last line **requires a change to an M1 file**, and it is the only one M2 makes. `run_fetch`
resolves the ticker at `fetch.py:135` and keeps the `TickerRow` in a local; `FetchResult` carries
neither `cik` nor `name`. So M2 adds both — `cik: int | None`, `name: str | None`, set in
`_resolve_ticker`, which already holds the row. Optional to match the dataclass's incremental-fill
style, and non-`None` by the time `run_fetch` returns because `_resolve_ticker` raises exit 2
otherwise. Recomputing them in the command instead would mean re-reading the 1 MB ticker file or
carrying a second resolution path, and `docs/m1/README.md` already rejects both.

Note that `run_fetch` already accepts `as_of` and `fetch` does not pass it, because `fetch` has no
`--as-of` flag. `facts` does, so `facts` is the first command that exercises that parameter
end-to-end.

**`--lookback` is not resolved twice.** `parse_lookback` runs at the command, and `window()` is
computed once and threaded down. Nothing under `normalize/` reads config and nothing reads a clock
— see [`05-testing.md` § 4](05-testing.md#4-new-layering-rules).

Sample output, and the four properties of it that are load-bearing, are in
[`04-serialize.md` § 6](04-serialize.md#6-the-facts-commands-table).

## 4. Exit codes

No new codes and no new error classes. `errors.ExitCode` (M0, §14) covers M2 exactly, which is
worth confirming because a milestone that needs a sixth code is a milestone that has misread §14.

| Condition | Code | Class |
|---|---|---|
| Ticker absent, or listed somewhere other than NASDAQ | 2 | `TickerNotFoundError` (M1) |
| Bad `--lookback` spelling, or under the 3y minimum | 5 | `ConfigError` (M0) |
| `--as-of` in the future | 5 | `ConfigError` (M0) |
| User-Agent unset; unknown price provider; missing provider key | 5 | `ConfigError` (M0/M1) |
| Retries exhausted, transport error | 4 | `UpstreamFetchError` (M1) |
| No `companyfacts` published for the CIK | — | absence; exits 0 and prints it |
| A metric resolves to nothing in every period | — | coverage, not an error |
| Fewer than 12 quarters of history | — | recorded on the history; §5.1's refusal is M5's |
| SIC 6000–6499, or 6798 | — | recorded; §6.10's refusal is M4's and M5's |

**`facts` never exits 3**, and that is a reading of §14 worth making explicit because thin coverage
is exactly the situation that invites it. Exit 3 is "insufficient data, **report still written**" —
`facts` writes no report, so returning 3 would promise an artifact that does not exist. Raised as
[spec question 12](#7-spec-questions) and tested by
`test_facts_command::test_thin_coverage_exits_0`.

This extends M1's own reading — *"404 and a missing tag are absences, not failures; the command
that needs the data decides whether the absence is fatal"* — one command further. `facts` never
needs the data; it reports on it.

## 5. The seams

### M1/M2, inherited

> No module under `ingest/` may reference `Metric`, and no module under `ingest/` may contain a
> `us-gaap` tag literal.

Enforced by `tests/test_layering.py` since M1. M2 is the layer that rule was protecting, and M2
adds the converse half.

### M2/M3, new

**`normalize/tags.py` is the only module in the package that may contain a `us-gaap` literal.** M1
argued the rule for `ingest/` on the grounds that a tag literal there *"is the first line of a
second, shadow copy of `normalize/tags.py` — and the failure mode of two tag tables is that the
report and the appendix disagree about which tag won."* The argument is stronger for `report/` and
`analyze/`, because those have a plausible reason to want one — a chart label, a hardcoded fallback
for a metric that came back empty — and the disagreement it produces is between the number and its
own provenance line. Widening the existing allowlist to one key
([`05-testing.md` § 4](05-testing.md#4-new-layering-rules)) makes M3 physically unable to
re-resolve a chain.

Three more, in the same spirit:

- **M2 assigns no severity.** §6.2 gives severity to `analyze/flags.py`'s registry, one rule per
  file with its own test. M2 emits `Finding` records with a stable `code` and no severity; M4
  decides what they mean. Two copies of a severity scale diverge on the first rule M4 tunes.
- **M2 makes no refusal.** §6.10's bank/REIT and §5.1's 12-quarter gate both suppress the
  *valuation* in a report that still gets written. A refusal reached inside normalization is a
  refusal with no report attached, which is the opposite of what §6.10 asks for.
  [`03-statements.md` § 5](03-statements.md#5-the-two-gates-m2-records-and-does-not-enforce).
- **`serialize.py` returns a string and does not write.** The command owns the file. Keeps the
  serializer pure and makes §11's determinism assertion a string comparison rather than a
  filesystem fixture.

## 6. Dependencies M2 adds

**None.** Per CLAUDE.md, dependencies arrive with the milestone that imports them, and every part
of M2 is `Decimal`, `date`, `json` and `dataclasses`.

Three deliberate non-additions, each of which is the obvious thing to reach for:

- **No `pandas`.** §2 names it in the ecosystem rationale and M5 will want it for the state-space
  fit. But M2's data is a few hundred `Fact` records per company with heterogeneous provenance
  attached to each, and a DataFrame is the wrong shape for that: the moment a value moves into a
  column, its `SourceRef` does not come with it, and §3.2's rule is that an untraceable number is
  not printed. Keeping the provenance welded to the value through the whole of M2 is the property
  the milestone exists to establish. `pandas` arrives in M5, over series that have already been
  reduced to numbers.
- **No `pydantic` for `report.json`.** The serializer writes a document from frozen dataclasses;
  the validation `pydantic` would add is on the read side, and there is no reader
  ([`04-serialize.md` § 7](04-serialize.md#7-what-serializepy-does-not-do)). `pydantic` is already
  present via `pydantic-settings`, so this is a decision not to use what is there rather than a
  dependency question.
- **No `jsonschema`.** `schema_version` is an integer contract with one version and one producer.

## 7. Spec questions

Seventeen — twelve from the design pass, five raised on review. Ordered by how much the answer
changes M2. Each is a place the code will diverge from
DESIGN.md, and the reason has to survive the person who finds the divergence in a year. **None
should be resolved in code.**

**Two of the seventeen change documented behaviour rather than internals, and they are the two most
likely to be skimmed past on the way to coding: 4 (`facts --json`, a CLI-surface change needing a
README § Usage line and a `_FLAG_OWNER` entry) and 12 (`facts` never exits 3).** Both are checked
bidirectionally by `tests/test_cli_surface.py` already, so the process catches 4 — it will simply
fail the build until README is updated. Nothing catches 12 except the test named in
[§ 4](#4-exit-codes).

**1. §4.2's "first match wins" does not say at what granularity, and the two readings disagree on
every filer with a long history.**

Series-level resolution — walk the chain once, use that tag for the whole series — loses two of
Apple's four annual revenue periods and reports full coverage on the two it keeps, because Apple
used `SalesRevenueNet` before FY2018 and the ASC 606 tag after. §4.2 requires the stitch
(*"long histories **must** stitch across the boundary or the series has a hole"*) without saying
what mechanism produces it.

Proposed: **period-wise**. Each period resolves through the chain independently, so the stitch is
the absence of a bug rather than a special case keyed on 2018, and the tag chosen for a period does
not depend on what else is in the window — a series-level primary would make the same fiscal year
resolve differently under `--lookback 5y` and `10y`, and §9.1's appendix would print two answers
for one fact. Spec'd in [`01-tags.md` § 1](01-tags.md#1-resolution-is-period-wise-and-this-is-the-decision-the-milestone-turns-on),
with the mixing risk handled by exclusivity groups rather than by the algorithm.

**2. "% of periods filled" has no denominator, so ROADMAP M2's ≥90% exit criterion is not yet
measurable.**

The three plausible denominators differ by more than the margin the criterion is testing: periods
in the requested window makes coverage measure company age; periods for which any fact exists is
circular; periods the company actually reported is the one that measures tag coverage.

Proposed: a **period spine** built from the filing history — `report_date` on 10-K/10-Q, amendments
collapsed, annual report dates counted as quarterly ends too — with an `OBSERVED` fallback that is
labelled everywhere it is printed, because a 100% figure computed against a circular denominator is
the most misleading number this milestone could produce. Spec'd in
[`03-statements.md` § 2](03-statements.md#2-the-period-spine).

**3. `FinancialHistory` and `CoverageReport` are §3.2 sketches, and the final forms add fields.**

`FinancialHistory` gains `name`, `sic`, `sic_description`, `window`, `quarters_available`,
`restatements` and `market_cap`, and retypes `dict[Metric, list[Fact]]` to
`Mapping[Metric, tuple[Fact, ...]]` — a frozen dataclass holding a mutable dict is frozen in name
only, and §11's determinism gate needs the series unable to change between build and serialize.
`CoverageReport` is per-metric with tier aggregates rather than one number, because ROADMAP M2's
criterion is stated per tier and a single aggregate hides a tier-2 failure behind tier-1 success.
Spec'd in [`03-statements.md`](03-statements.md).

**4. `facts` needs `--json`, which is a documented-flag-surface change.**

ROADMAP M2 puts `report/serialize.py` in this milestone. `facts` has no `--out` and should not get
one. Without a flag, M2 ships a serializer no command emits, so §11's determinism gate has no
end-to-end path until M3.

Proposed: `investo facts TICKER --json` writes the `report.json` document to **stdout**. No `--out`
needed, composes with redirection, and it is consistent with `docs/m1/README.md` § 3, which
declined `--json` on `fetch` on the grounds that *"`report.json` (M2) is the machine-readable
surface this project already committed to"* — an argument for putting it on the M2 command. Costs
one README § Usage line and one `_FLAG_OWNER` entry, per CLAUDE.md convention 5.

**5. Sign conventions are unspecified, and the failure is silent and filer-dependent.**

`PaymentsToAcquirePropertyPlantAndEquipment` is filed positive; §5.3's build subtracts capex. A
chain member signed the other way — `InterestIncomeExpenseNet` for interest expense — hands M5 a
series that is right for most filers and inverted for a few, in the direction that flatters them.

Proposed: each chain declares the convention M2 emits, the flip is a property of the **chain
member** rather than a response to observing a negative value, a flip produces a
`Derivation(rule="sign_normalized")`, and a fact contradicting the convention is kept and counted
as a finding rather than silently corrected. Spec'd in [`01-tags.md` § 8](01-tags.md#8-sign-conventions).

**6. §4.2 names the tier-2 tags but does not order them, and the orderings here are proposals.**

§4.2's tier-1 chains carry measured entity counts from the CY2025Q1 frames API. Tier 2 is a
sentence listing eleven concepts with no counts and no fallbacks. The chains in
[`01-tags.md` § 4](01-tags.md#4-tier-2--what-the-fzm-scores-need) are this document's, and they are
its weakest-evidenced part. They should be confirmed against a frames pull during the
[§ 3 coverage measurement](05-testing.md#3-the-coverage-measurement) rather than accepted on
review, and revised in the same commit as `COVERAGE.md`.

**7. SG&A is a sum, not a substitution, and the chain type has to say so.**

A filer reports either `SellingGeneralAndAdministrativeExpense` or
`GeneralAndAdministrativeExpense` and `SellingAndMarketingExpense` separately. Substituting one
component for the combined figure understates the metric by the other, silently — and Piotroski's
margin test would then improve for a filer that changed its presentation.

Proposed: a `Member` variant naming two tags and requiring **both** present for that period. It
leaves the resolution algorithm unchanged (the member matches the period or it does not) and
produces a `Derivation` naming both refs.

**8. Q4 derivation needs an aggregation class, and §4.2 does not have one.**

§4.2(c) gives `Q4 = FY − (Q1+Q2+Q3)` without qualifying which metrics it applies to. Applied to
diluted EPS it is arithmetically well-formed, plausible on sight, and wrong whenever the share
count moved during the year — which is most of the NASDAQ universe, and most wrong for exactly the
fast-diluting companies whose EPS matters. Applied to a balance-sheet metric it is meaningless.

Proposed: `FLOW | INSTANT | PER_SHARE` on each chain, plus a `subtractable` flag so
`SHARES_DILUTED_WEIGHTED` can bucket as a duration without being subtracted. Spec'd in
[`01-tags.md` § 6](01-tags.md#6-aggregation-class).

**9. YTD and `OTHER` were deferred to M2 by `docs/m1/README.md` spec question 6. Answering both,
and confirming the narrow duration bands.**

`YTD` is differenced only where it recovers a period the filer did not report discretely, never
carried into a series as-is, and dropped as redundant otherwise. `OTHER` is dropped and **counted
per metric** — a filer whose facts are 40% `OTHER` has had a fiscal-year change, which is a §6.4
finding rather than an ingestion detail.

The narrow bands (annual 350–380, quarterly 80–100, against SEC's frames tolerance of 335–395 and
61–121) are confirmed as deliberate: they refuse an ambiguous duration rather than mislabelling it,
and a 61-day period admitted as a quarter is a two-month stub charted as a quarter of revenue. The
per-metric `OTHER` count is what makes the cost of that choice measurable rather than assumed.

**10. §4.2's total-liabilities fallback must use the including-NCI equity tag, and the natural way
to write it does not.**

§4.2's table gives the derivation as `LiabilitiesAndStockholdersEquity −
StockholdersEquityIncludingPortionAttributableToNoncontrollingInterest`, and separately gives
`EQUITY` as `StockholdersEquity`, parent-only. Written as `L&SE − Metric.EQUITY` — which is how it
reads once `EQUITY` is a resolved metric sitting right there — the result overstates liabilities by
exactly the noncontrolling interest, for the ~11% of filers §4.2 says never tag `Liabilities` at
all.

Proposed: cross-metric derivations name their own tags rather than composing over `Metric`, and the
parent-only fallback, where the including-NCI tag is absent, emits a finding. The general form —
*a metric is a selection, and two selections that share a name do not share a definition* — is
worth stating somewhere normative.

**11. §4.5 does not specify `report.json`'s shape, and two choices here are hard to reverse.**

Proposed: source refs are **interned** into a top-level `sources` array and referenced by index,
with an integer meaning a `SourceRef` and an object meaning a `Derivation` — because §4.5's stated
purpose is `investo diff`, and with inline refs a single restated value diffs as a changed number
plus forty lines of identical provenance. And **values serialize as JSON strings, not JSON
numbers**, because a JSON number is an IEEE double to most parsers and
`391035000000.01` — the value the AAPL fixture carries specifically to catch this — reads back
wrong. Spec'd in [`04-serialize.md`](04-serialize.md).

**12. `facts` never exits 3.** A reading of §14 rather than a contradiction of it, listed because
thin coverage is the situation that invites it and because it decides the exit code on a real and
common input. Exit 3 promises a written report; `facts` writes none.

### Raised while reviewing (2026-07-31)

Five more, in the same form, from a read of the accepted set against the M1 code. The first is a
hole rather than a refinement; it is recorded here rather than folded silently because a document
that closes every hole this carefully should say when it missed one.

**13. `build_history` took `facts` and `profile` non-optionally, and both are `| None` in M1.**

`FetchResult.facts` is `CompanyFacts | None` and `FetchResult.profile` is `CompanyProfile | None`,
with live absence paths at `fetch.py:191` (no submissions payload) and `fetch.py:253` (no
companyfacts published). [§ 4](#4-exit-codes) lists the second as a normal exit-0 outcome of
`facts`. The signature contradicted both: it would not type-check under strict basedpyright against
`FetchResult`, and the first thin-coverage ticker would crash on a documented, common condition.

Resolved by widening both, keeping the two absences **independent** because they degrade
differently, taking `cik` and `name` as separate arguments so a submissions 404 does not lose the
company's identity, and widening `FinancialHistory.fiscal_year_end` to `str | None` since there is
no honest value to invent for a filer with no `CompanyProfile`. An absent `companyfacts` yields an
empty history with a `companyfacts_absent` finding, not an exception — §6.10's *"a blank space with
an explanation beats a confident wrong number,"* and a traceback is not a blank space with an
explanation. Spec'd in [`03-statements.md` § 1](03-statements.md#both-payloads-are-optional-because-m1-already-makes-them-optional).

**This is also the one change M2 makes to an M1 file.** `FetchResult` gains `cik: int | None` and
`name: str | None`, set in `_resolve_ticker`, which holds the `TickerRow` today and discards it
(`fetch.py:135`). Without them the command has no identity to pass when `profile` is `None`, and
the alternatives — re-reading the 1 MB ticker file, or a second resolution path — are both things
`docs/m1/` already rejected.

**14. The spine gave no tolerance between `report_date` and a fact's `period.end`.**

Every other date comparison in this design carries an explicit ±3 days because filers record period
boundaries inconsistently at the day level. The spine comes from the filing header and the fact end
from the XBRL context — two different fields — so exact equality would silently *undercount*
coverage on any filer whose two disagree by a day, in the one number that gates the milestone.
Resolved as nearest-within-3-days and **one-to-one**, with inexact matches counted; one-to-one
because otherwise two facts a day apart both satisfy one slot and push `filled` past `expected`.

**15. `Resolution` could not represent the SG&A summing member.**

`fact: RawFact | None` cannot carry a value summed from two separately-tagged facts, and computing
the sum in `facts.py` would put tag knowledge outside `tags.py` — the thing the `us-gaap` allowlist
exists to prevent. Resolved as `facts: tuple[RawFact, ...]`: empty is an absence, one is a filed
fact, more than one is a `Derivation` over all of them, and `tags_used` reports every tag so the
appendix does not imply one tag produced the number.

**16. Exclusivity groups could reproduce the ASC 606 failure at group scope.**

Majority-wins assumes a filer using two members of a group is noise. A filer that switches
*permanently* — a new tax nexus makes assessed taxes material — would have its minority periods
pushed silently down the chain to a weaker tag: the same confidently-wrong shape, one level down,
with `SalesRevenueNet`'s hand-written exclusion no help because it is specific to that pair.

Resolved by the same signal that makes the ASC 606 stitch legitimate — **partition versus
interleave**. Contiguous prefix and suffix is a switch: stitch it and emit `exclusivity_switch`
with the boundary date. Alternating is noise: majority-wins. Derived from the data rather than
hardcoded, so a future group needs no exception to be handled correctly.

**17. Two defects in the probe and the command sketch.** `date(SELECTED_ON.year - 3, …)` raises on a
Feb-29 pin date — replaced with `domain.periods.window`, which floors to the first of the month and
is the project's existing tested answer to exactly this. And [§ 3](#3-investo-facts--the-command-surface)'s
pseudocode used a bare `today`; it now calls `date.today()` explicitly at the command boundary and
says why that is the only place below `cli.py` allowed to.

### One risk accepted, not resolved

**The twenty-name coverage universe can be chosen so the criterion passes.** Tag coverage
correlates with filer size, so twenty NASDAQ-100 names would measure around 97% and predict nothing
about the twenty-first company someone runs. [`05-testing.md` § 3](05-testing.md#3-the-coverage-measurement)
specifies a stratified universe — four per market-cap quintile, at least one bank, one REIT, one
filer under three years old, the seven fixture companies excluded — and records the tickers in
`COVERAGE.md` so the selection is auditable.

The residual risk is that §4.2's own numbers say some metrics cannot reach 90% at all:
`LongTermDebtNoncurrent` covers 1,532 of ~5,000 filers, and §4.2 calls that chain *"the weakest of
the set. Expect misses; mark leverage metrics low-confidence."* A gate that forces 90% there will be
met by adding a chain member that means something slightly different. If the measurement lands
under the criterion, the honest response is per-metric floors with the weak ones named — a ROADMAP
amendment made of evidence, not a code change.

**So a ROADMAP amendment part-way through M2 is an expected outcome here, not a failure**, and it
should be visible as such to whoever reviews the milestone. The failure mode this is guarding
against is the other one: hitting 90% on long-term debt by adding a chain member that means
something slightly different, which moves the number without improving the data and leaves the
report's leverage figures quietly wrong for the filers the member was added to catch.

## 8. Proposed additions to ROADMAP § Decided during design

If the above are accepted, these are the sentences to record:

- **Chain resolution is period-wise, not series-level.** The ASC 606 stitch is then structural
  rather than a special case, and tag selection does not depend on the lookback window.
- **Mutually incompatible tags are declared in exclusivity groups**, which is what enforces §4.2's
  "never mix within one series" — not the resolution algorithm.
- **Coverage is measured against a period spine derived from the filing history**, with a labelled
  `OBSERVED` fallback. "% filled" without a stated denominator is not a measurement.
- **Each chain declares an aggregation class and a `subtractable` flag.** Q4 is never derived for a
  per-share or instant metric, nor for a weighted-average share count.
- **Each chain declares one acceptable unit; facts in any other unit are excluded and counted.**
- **Each chain declares a sign convention; a flip is a property of the chain member, not a response
  to the data, and produces a `Derivation`.**
- **Total liabilities is derived from the including-NCI equity tag**, never from `Metric.EQUITY`.
  Cross-metric derivations name tags, not metrics.
- **YTD is differenced only to recover a period the filer did not report discretely; `OTHER` is
  dropped and counted per metric.** The narrow duration bands stand.
- **Superseded restatement values are retained** in the `Restatement` record, which keeps ROADMAP
  open question 10 answerable later without a re-parse.
- **M2 assigns no severity and makes no refusal.** Findings carry a stable code; §6.2's registry and
  §6.10's gate are M4's and M5's.
- **`normalize/tags.py` is the only module that may contain a `us-gaap` literal**, widening M1's
  `ingest/` rule to the whole package with a one-key allowlist.
- **No sort under `normalize/` or `report/` may use a partial key**, since `FiscalPeriod` compares
  on `(end, kind)` and a stable sort over ties returns payload iteration order.
- **`report.json` interns source refs and serializes values as strings**, asserted on the
  serialized bytes rather than by a round-trip, which passes either way.
- **The chain registry holds exactly one summing member**, asserted, so a second is a visible edit.
- **The tier-2 chain orderings are provisional until `COVERAGE.md` exists** and are revised in the
  same commit as the measurement. Tier 1's are not — §4.2 carries measured counts for every member.
- **`facts` gains `--json` and never exits 3.**
- **M2 adds no dependencies. `pandas` arrives in M5**, after provenance has been discharged.
- **M2 is re-estimated at ~3.5 weeks part-time**, against ROADMAP's ~1.5 weeks; ~4.5 days of that
  is research rather than coding and should run in parallel from day one.

## 9. Sizing

ROADMAP budgets M2 at ~1.5 weeks part-time and marks it the hardest phase. That estimate predates
this design. M1's equivalent line was re-estimated at roughly double, and the same thing happens
here for the same reason: the design adds machinery that is justified and was not in the original
count.

| Workstream | Estimate | Notes |
|---|---|---|
| `tags.py` — registry, period-wise resolution, exclusivity, units, signs | 2.5 d | The registry is a table; the two-pass exclusivity re-resolution and the sign/unit declarations are the work |
| Cross-metric derivations + the acyclicity check | 1 d | Small, but the NCI trap and the recursive `Derivation` are where it goes wrong |
| `facts.py` — `as_of`, dedup, buckets, residual recovery | 3 d | The five guards on residual recovery are most of it, and most of that is test code |
| `statements.py` — spine, `CoverageReport`, findings | 2.5 d | The spine's four construction rules each have a failure mode worth a test |
| `serialize.py` — schema, interning, determinism | 1.5 d | Interning ordering and the subprocess determinism assertion |
| `facts` command + table rendering | 1 d | |
| Six new synthetic fixtures | 1 d | `make_fixtures.py` exists; the traps have to be constructed to actually fire |
| Six new layering rules | 0.5 d | AST machinery exists from M1; these are predicates over it |
| **Fixture curation** (carried from M1) | **3 d** | **Research. No green test. Blocks the first exit criterion.** |
| **Coverage measurement over 20 names** | **1.5 d** | **Research. Universe selection, the probe, `COVERAGE.md`.** |
| **Total** | **~17.5 d** | ≈ **3.5 weeks part-time**; ~13 d of it coding |

ROADMAP's own guidance on this phase is *"budget generously. If it runs long, cut M6 scope, not
this."* The estimate is worth having even if it is wrong, because the alternative is discovering it
in week four.
